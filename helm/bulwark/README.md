# Bulwark Helm chart

Deploys the core product -- Postgres, Redis, S3-compatible object storage, OpenBao, the API, the
Celery worker, a single-replica Celery beat, and the web app -- to Kubernetes, with an optional KEDA
`ScaledObject` that scales the worker on Celery queue depth (plan §23, Week 50).

Live-verified against a real `kind` cluster: every pod reaches Ready, a real KEDA installation reads
real Redis queue depth and scales the worker Deployment from 1 to 5 replicas on a real 3,000-task
backlog (draining it in under 30 seconds), and scales back down once idle. See
`docs/v2-week50-verification.md` for the full record.

## Quickstart

```bash
# 1. A cluster. kind works for local verification; any real cluster works too.
kind create cluster

# 2. KEDA (not installed by this chart -- it's cluster infrastructure, like Kubernetes itself).
helm repo add kedacore https://kedacore.github.io/charts
kubectl create namespace keda
helm install keda kedacore/keda -n keda

# 3. Load local images if your cluster can't pull them from a registry (kind-specific).
kind load docker-image bulwark/app:dev
kind load docker-image bulwark/web:dev

# 4. Install.
helm install bulwark helm/bulwark
```

## What this chart deliberately does not reproduce from docker-compose.yml

Every simplification below is a disclosed, intentional scope decision for Week 50's "Scale" work
(the autoscaling/load-testing/cost-visibility story), not a silent gap. None of them are hidden from
`values.yaml`'s own comments either -- this file collects them in one place.

- **Postgres has no mTLS.** `docker-compose.yml`'s own Postgres image (`bulwark/postgres:16-pgvector`)
  requires client certificates generated by `scripts/gen-mtls-certs.sh` and refuses to start without
  them mounted. Reproducing that in Kubernetes needs a certificate-issuing mechanism (cert-manager, or
  a chart-managed CA Job) this chart doesn't provide. The default here is the plain upstream
  `pgvector/pgvector:pg16` image with password auth -- the same substitution this repo's own CI
  workflow already makes for its RLS tests (`.github/workflows/ci.yml`'s `tenancy-rls` job). Postgres
  Row-Level Security itself is unaffected: `FORCE ROW LEVEL SECURITY` (ADR-0013) applies regardless of
  which role connects, mTLS or not. `postgres.image` and the connection string in
  `templates/secret.yaml` can be pointed at a real mTLS-fronted Postgres once such a mechanism exists;
  the app's own `BULWARK_DATABASE_URL` format doesn't change either way (it's an ordinary libpq
  connection string, `sslmode`/certs and all).
- **OpenBao runs in dev mode.** Same posture as `docker-compose.yml`'s own `openbao` service: a fixed
  root token, nothing survives a restart. A real deployment points `BULWARK_OPENBAO_ADDR` at a real,
  unsealed, persistent OpenBao instead of this chart's `openbao` Deployment.
- **The worker's scanner execution uses a privileged Docker-in-Docker sidecar, not socket-proxy.**
  `docker-compose.yml`'s worker reaches a narrow, allowlisted subset of the Docker API
  (`CONTAINERS`/`POST`/`IMAGES`/`VOLUMES` only) through `tecnativa/docker-socket-proxy`, which itself
  mounts the *host's* Docker socket. Kubernetes nodes don't expose a host Docker socket the way a
  compose host does, so `templates/worker.yaml` runs a `docker:27-dind` sidecar in the same Pod instead
  -- a real, commonly-used pattern (the same one many CI systems use to run Docker-based jobs on
  Kubernetes), live-verified to actually launch scanner containers correctly. The real, disclosed
  trade-off: DinD needs a **privileged** container, which is a materially broader security surface than
  socket-proxy's deliberately narrow allowlist. `worker.dind.enabled: false` turns this off entirely
  (the worker then has no way to launch scanner containers at all) for a cluster policy that forbids
  privileged Pods.
- **The shared upload workdir is a `hostPath` volume by default -- single-node only.** The API writes
  an uploaded archive to `BULWARK_WORKDIR` and the worker reads it by the same path (`core/config.py`);
  this needs a filesystem both Pods can see. The default `hostPath` PersistentVolume only works
  correctly when api and worker land on the same node -- true by construction on a single-node cluster
  like `kind`, false on a real multi-node one. Set `workdir.existingClaim` to a PVC backed by a real
  ReadWriteMany StorageClass (NFS, EFS, Longhorn, ...) for a multi-node deployment.
- **`web.publicApiUrl` only reaches server-side code, not the browser bundle.** Next.js inlines
  `NEXT_PUBLIC_*` variables into the client-side JavaScript bundle at **image build time**
  (`web/Dockerfile`'s `ARG NEXT_PUBLIC_API_URL`), not at container start. Setting `values.web.
  publicApiUrl` changes the runtime env var `web/proxy.ts` reads server-side per request, but a
  browser calling the API directly (`web/lib/api.ts`'s bundled `API_URL` constant) still uses whatever
  URL the image was built with. A real (non-port-forwarded) deployment needs the web image rebuilt with
  the real public API URL as a build arg.
- **The verified-fix agent (Temporal + `fixagent-worker`) and the observability stack (Prometheus,
  Jaeger, Grafana) are not in this chart at all.** Both are optional, `profiles`-gated services in
  `docker-compose.yml` too; adding them to Kubernetes is real, separate work this chart doesn't
  attempt.

## Celery beat is a dedicated scheduler, not a reduced-concurrency worker

`docker-compose.yml` runs one worker process with `-B` (embedded beat) and an explicit comment:
run exactly ONE worker with `-B`, because Celery beat scheduling a periodic task more than once per
interval (which happens if more than one `-B` process is running) means duplicate housekeeping, feed
refreshes, and crypto-shredding runs. Scaling the worker Deployment with KEDA means it can have
anywhere from 1 to `keda.maxReplicaCount` replicas, so `-B` cannot live there -- `templates/beat.yaml`
runs it as its own fixed-at-1-replica Deployment instead, using Celery's dedicated `beat` subcommand
(`celery -A core.tasks beat`), not `worker -B`.

That subcommand choice was not the first attempt, and the first attempt was wrong in a way only a live
test caught: an earlier version of this chart ran `celery worker -B -P solo -c 1` for beat, reasoning
(in a comment, no less) that "this process runs no task workers of its own" -- which is false:
`worker -B` is still a worker, just with concurrency 1, and it still consumes from the same `celery`
queue the KEDA-scaled worker Deployment does. This was caught directly: a 100-task backlog, pushed
onto Redis while the real worker Deployment was paused at 0 replicas specifically to build an isolated
backlog to scale from, quietly drained to 0 within seconds anyway -- beat's own solo worker was eating
it one task at a time, and KEDA never saw the depth it was supposed to react to. Switching beat to the
dedicated `beat` subcommand (scheduler only, never a consumer) fixed it, confirmed by rerunning the
same backlog test and watching the depth hold steady until the real worker Deployment resumed.

## Live-verifying the KEDA scaling yourself

```bash
# Build an isolated backlog: pause the worker Deployment at 0 replicas first, so nothing competes
# with the queue you're about to build (KEDA's `paused-replicas` annotation does this cleanly without
# fighting the ScaledObject's own reconciliation).
kubectl annotate scaledobject bulwark-worker autoscaling.keda.sh/paused-replicas="0" --overwrite

kubectl exec deploy/bulwark-api -- python -c "
from core.tasks import celery_app
for _ in range(3000):
    celery_app.send_task('bulwark.update_feeds')
"

# Confirm the backlog actually built up (nothing was consuming it).
kubectl exec deploy/bulwark-api -- python -c "
import redis; print(redis.from_url('redis://bulwark-redis:6379/0').llen('celery'))
"

# Let KEDA resume and watch it react.
kubectl annotate scaledobject bulwark-worker autoscaling.keda.sh/paused-replicas-
kubectl get hpa keda-hpa-bulwark-worker -w
```
