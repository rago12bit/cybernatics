    Evaluation v2 (plan §34, Week 52)¶

    Every row of the plan's own evaluation table, filled in honestly: measured and cited where real work already exists, freshly measured this week where that was feasible without a live model, and clearly marked not measured where it genuinely isn't -- most commonly because the feature needs a live ANTHROPIC_API_KEY this environment does not have, a gap every one of those features' own weekly verification docs already disclosed individually. This document's job is to put all eleven rows in one place, not to re-litigate or soften what they already said.

    Taint engine: what was actually measured¶

    The taint engine (core/taint/) doesn't detect vulnerabilities on its own -- it confirms whether a SAST finding some other scanner already reported is reachable from a real HTTP entrypoint (core/taint/reachability.py's own documented design). So "precision and recall on labelled cases" means: of the SAST findings it could confirm, were the confirmations correct, and of the ones it could have confirmed, how many did it?

    Method. Ran the real scan pipeline (bulwark scan --tools bandit,semgrep, no mocks) against 8 already-cached, real, deliberately-vulnerable repositories from this project's own 25-repo corpus -- every Python/JavaScript one it has (NodeGoat, nodejs-goof from Week 52; VAmPI, Vulnerable-Flask-App, pygoat, dvpwa, vulpy, dvna added afterward) -- then read the flagged source by hand to check each confirmation against the real code. Full method, two real bugs found and fixed along the way (a resolver name-collision that could silently erase real taint, and a missing subprocess.Popen catalog entry), and three freshly-confirmed real scope limits: docs/v2-gap-closure-taint-corpus.md.

    Result: 9 confirmed reachable findings across 5 of 8 repositories, 9/9 hand-verified genuine true positives, 0 false confirmations -- up from the original 3/3 on NodeGoat alone: - NodeGoat (unchanged): 3 findings, app/routes/contributions.js:32-34, eval(req.body.preTax) et al. -- NodeGoat's own documented "A1 SSJS Injection" tutorial vulnerability, the file's own comment reads // Insecure use of eval() to parse inputs. - pygoat: 4 SAST findings confirmed reachable (cmd_lab's and mitre_lab_17_api's subprocess.Popen command injections, cmd_lab2's and mitre_lab_25_api's direct eval injections -- one of the four only found after this week's bug fixes, see the linked doc), plus a 5th genuine reachable sink (ImageMath.eval) with no SAST finding at that exact line to attach to. - Vulnerable-Flask-App: 1 (request.json-sourced SQL injection via db.engine.execute). - dvna: 1 (req.body.login-sourced SQL injection via db.sequelize.query). - VAmPI, dvpwa, vulpy: 0 confirmed each, for three different, real, documented reasons (an OpenAPI-path-parameter source the catalog doesn't recognize; an ambiguous same-named function across the repo's own parallel bad/good implementations; an aiohttp app, a framework core.codeintel's entrypoint detector doesn't cover) -- not silent gaps, each confirmed and named in the linked document. - Every confirmed finding's originating SAST rule fires on the pattern alone (eval(), subprocess.Popen(..., shell=True), a raw .execute()/.query() call), tainted or not -- the taint engine's actual contribution is narrowing each one down to "and this argument provably comes from this HTTP request," which the pattern rule alone cannot say.

    What this is not: a corpus-scale precision/recall study, and not a comparison against Semgrep's own taint mode specifically (its bundled community rules use pattern mode here; a taint-mode comparison would need hand-authored Semgrep taint rules for the same source/sink pairs, which wasn't built). This is a real, hand-verified spot-check, larger than before -- 9 confirmed cases across 8 repositories, 0 false confirmations -- not the full "labelled Python and JavaScript corpus" the plan describes, and no Go-language vulnerable repository exists in the corpus at all.

    The risk score leads at every K, but every confidence interval includes zero -- this is weak evidence in its favor, not a demonstrated result. "Severity only" here is a fair stand-in for v1's own pre-EPSS/KEV ranking, since that's literally what v1.0 sorted by before Week 9 added EPSS and KEV. The parts of the score that matter most for dependency findings (EPSS, KEV, reachability) have no exploitation ground truth in this dataset, so their effect on ordering is argued in risk-score.md, not measured here -- unchanged since the original measurement.

    LLM security detail¶

    tests/redteam/ (see docs/redteam.md) runs 20 adversarial payloads against every contract that parses raw model text (core.llm, core.triage_assistant, core.attackpath) -- 60 payload x contract combinations, all 60 correctly rejected, plus four more targeted suites (patch confinement, severity immutability under injection, Copilot tool-scope enforcement, a real secret-forwarding bug this suite itself caught and fixed). This is a structural defense pass rate: it proves the contracts can't be tricked into producing a harmful result regardless of what a model says. It is not the plan's "attack success rate per release," which needs garak actually attacking a live model and tracking how often persuasion succeeds -- deliberately deferred, same reasoning docs/redteam.md already gives: that needs a real API key, ongoing spend per run, and a probe-budget decision, not something to fake with a hardcoded number.

    What this does NOT prove (read before relying on it)¶

    • Five of eleven rows need a live model and were not measured: verified-fix acceptance/blind review, triage assistant precision/recall, hypotheses lane precision, Copilot citation/correctness, and the LLM security attack success rate specifically (its structural-defense pass rate is measured, above). Every one of these gaps was already disclosed in that feature's own week (41/42/43/44) -- this document doesn't newly discover them, just collects them.
    • The UX row has no "before" or "after." The baseline usability study (Week 31) was never run with real participants; there is nothing to compare a redesign against yet.
    • The taint engine measurement is a spot-check (N=9 confirmed cases across 5 of 8 repositories), not a corpus-scale study, and makes no claim about recall against vulnerability classes outside its declared sink categories, or against the 4 corpus repositories whose own language (Java, CloudFormation, Terraform) has no taint catalog at all. The Go catalog specifically has never been run against a real vulnerable repository -- the corpus has none.
    • Scale and platform-security numbers are a single developer laptop's, not a provisioned server's -- see each one's own week for the full caveat.
    • Incremental scanning is 7 repositories with a 3-file edit each, not the plan's "last 20 merged PRs of each repository in the 30-repository corpus" -- benchmarks/incremental/run.py supports more repos; running it across the full corpus, and against real historical PRs rather than a synthetic edit, was not done. One repository (Vulnerable-Flask-App) showed a much smaller speedup (1.2x) than the rest, plausibly but not confirmed-as-root-caused to a Semgrep per-rule timeout on that repository: docs/v2-gap-closure-incremental-corpus.md.
